## Durable rules

1. **Check the code before trusting a doc.** Re-read the files a task touches. Never treat a "Planned" item in `PLAN.md` as already built.
2. **Follow `PLAN.md` task order.** After each task, update its checklist (§22), the log (§23) and any note about where the code differed from the plan.
3. **Keep existing behaviour.** The marketplace, checkout (`packages/lib/src/orders/place-order.ts`), wallets (`docs/wallet.md`), shipping and fulfillment (`docs/fulfillment.md`) must keep working. Make small changes, not rewrites.
4. **Stop and ask** before changing the agreed business model (`PLAN.md` §13), running a destructive or production migration, or changing money and ledger logic outside an approved task.
5. **Tenant isolation.** The `sellers` row (`sellers.id = users.id`) is the **account** (plan, wallet, trial, legal data). The planned **`stores`** table is the **tenant**: a seller can own several stores, up to the plan limit (Free = 3; `sellers.plan` defaults to `'free'`, and limits live in the code plans module). Server code bypasses RLS through Drizzle, so every query must check that the store belongs to the session's seller and filter child rows by `store_id`. On storefronts, the store comes from the request host. Store-scoped actions always take an explicit `storeId`; never use a "current store" cookie as the target of a write. Never trust seller or store IDs sent by the client. Hiding a UI element is not authorization.

7. **Money.** Compute in integer piastres and store in the existing `numeric(10,2)` columns. Ledger writes must be idempotent, using a unique claim plus `ON CONFLICT`. Store-wallet balances (seller ledger) change **only** through the planned `postStoreWalletEntry` primitive. Store wallets may be negative, customer `user_wallets` may not, and the two ledgers stay separate. The agreed fee is a flat EGP 5 per seller per delivered order, taken from the store wallet (which may go negative), with a 7-day free trial counted from the seller's first store `created_at` (`PLAN.md` §13, 0067) for sellers created before 0119. Sellers created after 0119 get no trial but an EGP 100 welcome gift in the store wallet when they finish setup, valid 30 days, unspent part taken back (`PLAN.md` §13.1, owner 2026-10-29).
8. **Caching.** Use `@workspace/cache` (`createCachedQuery`, tags in `packages/cache/src/tags.ts`, cross-app broadcast). Never cache carts, orders, wallets, builder drafts or integration secrets. Every cache key and tag for store data includes the seller ID.
9. **No seller-supplied code.** The builder has no custom HTML or JS nodes. Integrations inject scripts only from fixed templates, with IDs checked by regex, and only on that seller's storefront host.
10. **Secrets.** Never put secrets in `NEXT_PUBLIC_*`, client components, logs or docs. The service-role key stays in server code only.

Tallaby Classic is the default template again, rebuilt as tree sections (owner, 2026-10-19; `packages/store-sections/src/templates/classic/`, key `tallaby-classic`, v3 in `0071`). A never-published store (`site_status = 'draft'`, every new store) and an unpublished store (`site_status = 'unpublished'`, the seller's "Website live" switch off) are both **offline**: every storefront route shows the store-offline page (noindex) and `createOrder` refuses their carts, except in a verified builder preview; marketplace listings are unaffected (owner, 2026-10-21; `isStorefrontOffline` in `apps/ecommerce/lib/storefront.server.ts`, `apps/ecommerce/lib/store-site/offline.server.ts`). Only a published site is ever shown to visitors. Do not change the default template's design without the owner's approval.
17. **Sections are element trees.** Every website section and template is built as an element tree with `defineDesign` (`packages/store-sections/src/designs/<library-category>/<id>.ts`) and inserted as a `custom-section` whose single root is a `section` node, so every element can be selected, styled and moved (owner, 2026-10-19). Never write a coded `SectionDefinition` + `Component` section. **Templates and sections are code-only (owner, 2026-10-27):** `CODE_TEMPLATES` and `DESIGNS` in `packages/store-sections` are the single source; the `templates`, `template_versions` and `library_sections` tables are dropped (0109), the Admin template/section screens are commented out, and a design or template change ships with a deploy (no migration). Stores keep their own copies (drafts and live revisions), so a code change never alters an existing site.
